# Rule evidence upload reservations

This K018 slice implements the catalog upload-request POST and document-metadata GET for internal-sensitivity, rule-version-owned evidence only. Other owners and sensitivities remain unsupported. It creates an immutable upload reservation, not a retained capture or verified source. There is no completion, download, archive or scan control yet, and no upload UI is exposed.

The PostgreSQL reservation has composite organization/entity/rule foreign keys, scoped RLS and current finance-manager insertion checks. Runtime UPDATE/DELETE/TRUNCATE are withheld and history is append-only even for owner-role statements. A trigger validates the exact declaration, derives source references/demo status from the immutable owner and owns creation time. The declared SHA-256 must identify one source title/URL, possibly several sections; ambiguous same-hash source identities are rejected instead of silently choosing one. Sensitive worker/bank evidence cannot enter this rule-only workflow.

The pending response retains the document dictionary's storage key, original name, MIME and aggregate-owner fields. Its actual size/hash/uploader/capture time are explicitly null before server completion; declared size/hash live in the separate declaration. Retention is visibly unconfigured and no file deletion hold is claimed. These pending-only nulls represent unknown content, not successful capture or zero values. Completion must replace the pending response variant with actual retained metadata; it must not reinterpret declared values as verified facts.

The service locks scope, rechecks current creation authority and owner/profile access before replay, then commits reservation, scoped audit and durable idempotency response together. Missing configuration or audit failure rolls back all database effects. Replay preserves the original object identity, grant and expiry; it does not renew expired access. A new request/key is needed after expiry. Metadata GET never returns a signed URL. Actual hash, capture time and uploaded actor remain null; scan state remains quarantined even if the provider has received bytes.

An upload goes directly to private S3, not through the web function's body limit. The existing signer binds the random scoped key, exact Content-Length, MIME, If-None-Match and SHA-256 checksum in a five-minute PUT capability. The provider rejects header/body checksum changes, changed size, expiry, GET use and overwrite. The browser must let its Blob request set the matching Content-Length automatically and requires operator-configured private-bucket CORS. Current browser coverage verifies the setup failure with no reservation, not a completed browser upload. No endpoint or bucket-security configuration is changed automatically.

Signed URLs are short-lived bearer capabilities. Current authorization is required when issuing/replaying them; revocation cannot retract an already issued capability before its expiry. It is write-only, quarantine-only and single-object/create-only. Completion must reauthorize, pin actual object identity, validate bytes and persist immutable capture/scan/hold evidence. Missing scanner capability must block live release. Demo fixture admission must be explicit and remain isolated from live companies; an upload reservation does not admit a rule or grant posting authority.

Tests cover strict contracts/catalog parity; real PostgreSQL scope, source matching, roles, revocation, replay, immutability, SQL-owned metadata, raw SQL attacks, missing configuration and audit rollback; and real private-provider signature/size/MIME/checksum/expiry/overwrite enforcement. PostgreSQL signer tests use isolated test-only credentials without contacting storage; provider enforcement is proven separately with actual uploads. R1/K018 remain incomplete until capture and the rule lifecycle are implemented and accepted.

The signed-header protocol follows the [AWS signer documentation](https://github.com/aws/aws-sdk-js-v3/tree/main/packages/s3-request-presigner). No new storage dependency or provider is introduced. Original specifications and the finite API catalog remain unchanged.
