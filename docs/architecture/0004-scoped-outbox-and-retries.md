# Scoped policy outbox and bounded transactions

Status: implemented foundation; general jobs, scheduled dispatch and financial sources remain pending.

Policy activation synchronously commits its immutable source change, audit, durable command response and one typed `approval_policy.activated` event. The database enforces one event per organization/entity/kind/source/version. Events carry only source identity/version/hash and the activating principal/creator recipient, not arbitrary provider payloads.

The restricted runtime role claims a bounded explicit principal/organization/entity batch. Every claim and delivery establishes transaction-local scope, takes the existing organization lock, and rechecks current reviewer authority. The lock serializes execution against membership revocation. Recipient access and the source version/hash are checked again at delivery. Revoked recipients receive no alert; revoked principals cannot execute. There is no global worker identity, RLS bypass role, financial posting job or implicit external send.

Leases last 60 seconds and use random fencing tokens. A stale or expired token cannot complete or defer work. Attempts are capped at three, with bounded local retry delay and redacted failure codes. Process crashes leave recoverable leases; exhausted events remain inspectable. `outbox:process` runs one batch and exits. Automated dispatch and catalogued job inspection/manual retry are not implemented in this slice.

Local alert consumption uses a unique `(event_id,effect_key)`. Alert reads remain recipient-only, including acknowledgement reasons at SQL level. PostgreSQL `ON CONFLICT` requires existing-row visibility, so a narrowly defined migration-owned `emit_policy_alert(event,token)` function performs deduplication without granting reviewers SELECT access to recipient alerts. It validates the exact current scope/principal, live lease token, current reviewer/recipient permissions and source before inserting. No arbitrary recipient, message, table or payload is accepted. Direct runtime INSERT/DELETE on alerts is denied. The local effect and event completion commit together. Delivery is at least once; this does not promise infrastructure-wide exactly-once delivery.

Notification acknowledgement is a strict, version-bound, idempotent command. Current recipient authorization is checked before replay; source version is part of the canonical request hash. Changed input with the same key conflicts, lost responses return the original result, and stale new commands require reload. Acknowledgement audits metadata without duplicating the private reason into audit history.

`withScope` retries the entire BEGIN/scope/authorization/callback/COMMIT transaction at most three attempts with jitter, only for genuine PostgreSQL serialization/deadlock errors (40001/40P01). Rollback and pool release precede retry. Constraints, domain errors and ambiguous connection/commit failures are not retried. Callbacks must contain only database work; external side effects belong after commit or in separately designed consumers.

Runtime connection parsing accepts the restricted direct role or an exactly project-qualified Supabase transaction-pooler role. It rejects elevated roles and emits credential-free configuration errors. The project reference is metadata, not a connection credential. Local test URLs are preserved; no hosted database was reset or migrated as part of verification.

Evidence: runtime-config/transaction-retry unit tests; alerts contract tests; real outbox integration tests cover duplicate delivery, receipt privacy, source/effect rollback, concurrent claims, lease fencing/recovery/exhaustion, bounded errors, scope guesses, access revocation and transactional authorization rechecks. The approval-controls browser story covers actual worker delivery, private GET/strict acknowledgement API, persistence after reload and mobile layout. General R1-REPLAY acceptance still requires financial-source uniqueness and general job retry/recovery workflows.
