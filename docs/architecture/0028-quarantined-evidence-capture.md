# Quarantined evidence capture

K018 now has the finite catalog `POST documents/{id}/complete` operation, with strict `UploadComplete`, mandatory idempotency and If-Match, and a versioned document response. Completion means an immutable capture of independently read bytes; it does not mean successful scanning, retention configuration, rule review or release. No download/archive control or public upload UI is added.

The service reauthorizes current finance-manager access and the bound immutable rule owner/profile, including on a successful replay. It serializes the entity scope, discovers provider ETag/version through HEAD, and performs an ETag-conditional GET with the version pinned when provided. Both requests share a fifteen-second abort deadline. The existing bounded reader verifies exact MIME headers, size, content envelope and independently calculated SHA-256. Provider metadata or the submitted hash alone cannot substitute for those bytes. Content-envelope identification remains neither a complete parser nor a malware scan.

Forward migration 0034 stores one append-only capture per scoped reservation, with actual size/hash, provider ETag/optional version, storage origin/bucket, reservation issuer and current capture actor. The database owns capture time and issuer provenance, constrains size/hash against the immutable declaration, validates current scoped authority and demo profile, and rejects clean scan/hold labels. Runtime UPDATE/DELETE/TRUNCATE are withheld; an owner UPDATE/DELETE also hits the immutable-history trigger. SQL cannot contact the object store: the restricted service role and its storage credentials remain a trusted boundary for actual-byte provenance. A direct metadata insert cannot create scanning or download authority.

The metadata GET returns a discriminated resource: existing `pending_upload` version 1 with unknown actual values, or `captured_quarantined` version 2 with actual size/hash/time and actors. `uploadedBy` identifies the reservation issuer whose scoped PUT was issued; `capturedBy` identifies the authorized person completing the capture. A bearer PUT does not independently identify its physical user. Source sections, owner, sensitivity and synthetic status stay attached to the immutable reservation. Retention remains visibly `unconfigured`, deletionHold false and scanState `quarantined` in both variants.

Capture, scoped audit and durable receipt commit together. Same-key/same-body/version retries return the original receipt before stale-version rejection, after current authorization/profile checks. No provider access is needed for that historical replay; it does not certify the object's present availability. Changed input conflicts, concurrent different keys leave one capture and a stale-version loser, and audit failure leaves no capture or receipt. Invalid/missing bytes never produce a capture. The captured object is not locked against an operator with privileged storage credentials: future review/download must revalidate retained identity and bytes, and real retention/scan evidence must be implemented rather than inferred.

Verification includes an actual signed PUT → private provider HEAD/conditional GET → restricted PostgreSQL capture/audit/receipt → scoped DTO journey. CI installs the existing pinned local provider for that integration suite. Unit cases exercise the shared deadline, conditional identity, absent metadata and redacted failures. Browser coverage tests authenticated command schema/ID/If-Match/idempotency/origin/unknown-resource boundaries and absence of phantom records, not a successful file-upload interface. Production setup smoke is not hosted authenticated acceptance when the runtime database is unconfigured.

Next gates remain real persisted scan/retention/hold decisions, clean bound download and safe archive, the upload interface with operator-configured transport/CORS, independent persisted rule verification and evaluator test runs, version-bound activation/retirement and posting admission. Missing scanner blocks LIVE release; synthetic files never become clean/live by changing a label. K018 and R1 remain incomplete; K019 and later releases are not started.

Provider snapshot discovery follows the [Amazon S3 HEAD contract](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html); conditional content verification uses the existing reader. The original finite catalog and specification packages are unchanged. ADR 0027 describes the earlier reservation-only boundary and is superseded only for this capture operation.
