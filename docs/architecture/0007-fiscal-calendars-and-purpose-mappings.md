# Fiscal calendars, purpose mappings and source-bound numbering

Fiscal setup extends the accepted account chart with six catalog operations. Calendar dates remain ISO AD strings across PostgreSQL and application boundaries. Users supply one to twenty-four ordered, contiguous half-open periods rather than an inferred fiscal-year boundary. An active ordinary equity account and its immutable master version are retained on the year. Company-normalized labels are unique and fiscal calendars cannot overlap. Deferred SQL constraints require the complete declared calendar; a failed transaction rolls back periods and all eleven series with its header.

Finance managers configure setup; accountants and auditors read it. Organization administration does not grant financial mutation. Existing settings-read permission permits organization administrators to inspect mapping metadata, not chart names or balances. Every runtime query is scoped by transaction-local organization/entity/user settings and the restricted role. The shared organization lock serializes setup with membership changes and account archival. Missing scope explicitly denies access. Composite account-version references cannot cross companies.

A mapping revision requires all twenty-six finite R1 purposes, an effective date and a reason. This is an engineering completeness gate for future posting, not a statutory policy. Accounts must be active and match the exact ordinary/control classification. Compatible purposes may share an account; no seed chart is guessed. Empty configuration has version one; the first saved revision is version two. If-Match protects changes. Subsequent revisions must advance the effective date and cannot precede today's Nepal date. Previous revisions and their account-version references are immutable. Read responses distinguish the latest scheduled revision from the currently effective revision. Calendar retained accounts and current/future mapped accounts cannot be archived. Historical replaced mappings remain retained.

Calendar creation uses durable input-bound idempotency and returns the original calendar response, even if series counters later change. Location points to the catalog's fiscal-year collection; there is no uncatalogued year-detail endpoint. Mapping patches use optimistic concurrency, not an invented idempotency contract. Lost mapping responses require reloading current state; stale edits expose an explicit reload action. The screen paginates years and can load additional compatible account choices.

There is no public numbering route. The restricted SECURITY DEFINER allocator is called inside a future posting transaction. It checks current finance authority, exact scope and an open fiscal period, locks the series, retains an immutable source/type/event/date-bound receipt and advances the counter atomically. Concurrent replay returns one committed receipt. Failed posting rolls both counter and receipt back. Previously committed receipt replay remains possible after closing, but a fresh allocation in a closed period fails. Runtime callers cannot directly alter counters or receipts. Numbers contain document type, fiscal-year start date and a minimum six-digit sequence, unique per company. The counter bound is technical, not a statutory numbering prescription.

This setup does not post balances, certify reporting/tax rules or implement closing. K013 must atomically consume these mappings, account versions, period locks and receipts alongside immutable balanced journal/source records, and add posted journal/open-item/opening dependencies. K042 must introduce authorized audited closing/reopening transitions through a new migration; the current calendar rows cannot be edited by runtime SQL. Only generated fixture organizations in the dedicated local database are cleaned up by tests. No hosted database reset or migration is performed here.
